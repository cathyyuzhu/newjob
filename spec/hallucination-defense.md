# 这个项目怎么防 AI 幻觉

## 一、先说清楚：这个场景里的"幻觉"会造成什么后果

谈防幻觉之前得先知道防的是什么。这是一个求职助手——抓职位、跟简历做匹配分析、生成定制简历和 cover letter、准备面试。它的幻觉不是"答错一个知识点"这种可以一笑了之的事，具体有三种，代价一种比一种实：

**① 把简历里不存在的经历写进定制简历。**
最严重的一种。用户拿着这份简历去投递，面试时被问到那段经历——当场穿帮，而且是在最不该出问题的场合。

**② 匹配分数虚高。**
JD 白纸黑字写着 "PMP certification is required"，简历里没有，模型仍然给 0.85 分。用户按分数排序、优先看高分职位，时间被浪费在根本过不了硬门槛的岗位上。这个项目的实际数据佐证了这件事：37 条 ≥0.7 的职位里，11 条被人工否决（见 [product-review.md](product-review.md)）。

**③ 简历改写建议指错段落。**
这一种最隐蔽。AI 说"把第 5 段改成 XXX"，但它引用的原文其实是第 2 段的内容。应用下去会覆盖掉一段本不该动的文字——而且**用户不会收到任何提示**，只会拿到一份莫名其妙缺了内容的简历。

三种后果的共同点：**用户没有办法自己发现**。这决定了后面所有的取舍——防线必须建在用户看到结果之前。

## 二、对着"五层防幻觉框架"逐层判断

有一套流传比较广的五层框架：Prompt 层（元认知约束）、RAG 层（知识锚定）、生成控制层（低随机性 + 结构化解码）、后验证闭环层（一致性检测、引用溯源、置信度评分）、可观测性层（持续监控）。

这个框架本身是合理的思路，但**照单全收是错的**。逐层判断的结果：

| 层 | 判断 | 为什么 |
|---|---|---|
| ① Prompt | **做，但只是底线** | "不要编造"这类指令四个模块里都写了。它有用，但它是唯一一个模型可以选择不遵守的防线，不能当主力 |
| ② RAG | **明确不做** | 见下 |
| ③ 生成控制 | **做一半，且不是为了防幻觉** | 见下 |
| ④ 后验证 | **主力，投入最大** | 见第三节 |
| ⑤ 可观测性 | **做，而且最先做** | 没有度量就说不清前面几层有没有用 |

### 为什么 RAG 层明确不做

RAG 解决的是**检索**问题——从一个大语料库里找出跟当前问题相关的片段，再让模型基于这些片段回答。

这个项目没有检索问题。所有的 LLM 调用都是"单文档进单文档出"：这一份 JD 配这一份简历、这一个职位的自由问答、这一整份简历的体检。输入是什么，从一开始就是确定的。把结构化数据直接拼进 prompt 是**对的做法，不是偷懒**——硬要在中间插一层向量检索，只会引入一个新的出错环节（检索不准 → 模型看不到关键信息 → 幻觉更多）。

唯一有点"语料"形态的是面试题库，目前几十条，全量注入 context 完全放得下。**触发条件写在了 [tech-solution.md](tech-solution.md) 里**：等题库涨到几百上千条、必须截断到答案失真的时候，再给这一个功能单独接检索。

这一条是整个评估里最想强调的判断：**RAG 不是防幻觉的万能药，没有检索问题就不该引入检索。**

### 为什么生成控制只做一半

框架里说"低随机性 + 结构化解码"。把温度降到 0 确实有用，但它管的是**输出的稳定性和可复现性**——同一份 JD 分析两次，分数别差太多。对**事实性幻觉**基本没用：模型该编还是会编，只是编得更整齐。

而且这里有个硬约束：项目默认用的 `claude-sonnet-5` **已经从 API 移除了 `temperature`/`top_p`/`top_k`，传了直接返回 400**。所以"给所有调用加个 temperature=0"这种改法会让整条分析链当场崩掉。实际做法是先加一个按模型的开关（防 400 本身就是纯收益），温度值按任务性质给了保守初值——打分任务 0.0、面试题库创作 0.7、自由对话干脆不设——但**还没有用 eval 量过效果，所以没有把它当成一项"已经做好的防护"来讲**。

在这个模型上真正对症的是结构化输出（约束模型必须返回符合 schema 的 JSON），它能直接消灭"模型返回的根本不是 JSON"那一类失败。这一项识别出来了，但还没做——需要按任务逐个试点，schema 写错的代价是整个功能位报错。

### 为什么不做"验证器模型二次核查"和"置信度评分"

这两项是框架第四层里点名提到的，但都跳过了：

- **验证器模型二次核查**：让另一个模型检查第一个模型的输出。成本和延迟都翻倍，而且引入了第二个会编造的环节。这个项目的核心风险用确定性代码就能抓到（见下一节），不需要用模型查模型。
- **置信度评分**：让模型给自己的答案打个置信度。问题是 LLM 自报的置信度**校准很差**，普遍过度自信——一个编出来的答案往往和一个正确答案给出同样高的置信度。要拿到真正可信的置信度需要独立的验证器，绕回上一条。

项目里已经有的做法反而是这个方向上更务实的：**允许模型说"不知道"**。判断不出公司归属就填 `unknown`，对公司没有可靠认知就如实写"未找到该公司的相关信息"，简历信息不足以支撑某道面试题就在答案里标"（此处需你补充：…）"而不是虚构一段经历。

## 三、核心手法：用确定性代码核查模型的事实性断言

这是这个项目防幻觉的主线，也是最值得讲的一点：

> **不用另一个模型去查模型，而是让模型给出可被程序验证的证据，然后用普通 Python 代码回原文核对。**

零 LLM 成本、零额外延迟、结果 100% 确定。目前有两个落地点。

### 落地点一：段落改写建议必须对得上简历原文

这个例子最完整，因为它修的是一个**真实存在的数据损坏路径**。

先看机制。简历被读成带索引的纯文本喂给模型：

```
[0] 张三
[2] 负责用户增长项目，带领 3 人团队。上线后次日留存提升 12%，月活从 40 万涨到 55 万。
[5] 熟悉 A/B 测试、埋点体系设计。
```

模型返回改写建议，格式是 `{index, original, text}`——`original` 是它声称照抄的该段原文，`text` 是改写后的整段。应用时按 `index` 把对应段落**整段替换**掉。

问题就在"整段替换"这四个字。假设模型返回：

```json
{"index": 2, "original": "负责用户增长项目，带领 3 人团队。", "text": "主导用户增长项目，带领 3 人团队。"}
```

它只摘抄了这一段的**前半句**，也只改了前半句。但应用是整段替换——"上线后次日留存提升 12%，月活从 40 万涨到 55 万"这句量化成果会被**静默删掉**。简历上最有说服力的那句话没了，用户不会收到任何提示。

**核查做法**：模型说第 2 段的原文是 X，那就把真正的第 2 段拿出来比一比。归一化之后（去掉索引标记、全角转半角、压缩空白）分四种情况：

| 情况 | 判定 | 处理 |
|---|---|---|
| 一字不差，或相似度 ≥ 0.90 | 通过 | 正常应用。0.90 的容差是留给"少个句号、中文引号写成英文引号"这类誊写偏差的 |
| `original` 是真实段落的**子串** | 只摘抄了一部分 | **拦截**——就是上面那个静默删内容的情况 |
| 差得多 | 索引指错段了 | **拦截**——应用会覆盖本不该改的内容 |
| 模型没给 `original` | 无法核实 | 放行，但用真实段落把它补上 |

**被拦截的建议不是删掉，而是展示出来并标记成不可应用**（勾选框禁用 + 一句说明"AI 引用的原文跟这一段对不上，应用后会覆盖掉本不该改的内容"）。这是刻意的：直接过滤掉的话，用户永远不知道 AI 指错过段；把校验结果显性化，正是这一层存在的意义。

另外无论哪种情况，界面上"原文"那一栏**永远显示真实的段落文本**，模型给的那份被挪到另一个字段。用户看到的原文不再是模型的复述。

最后，用户点"生成优化版"的时候，**服务端会对着当前简历再核查一遍**，不信任前端传回来的内容。这不只是防篡改——有一条完全正常的路径会触发它：用户重新上传了简历，然后回头应用之前那次体检的建议，段落索引已经全部错位了。

### 落地点二：硬门槛封顶必须有 JD 原话为证

这一条针对的是"匹配分数虚高"。

prompt 里一直写着一条规则：JD 里明确标注为强制性的要求（required / must have / 必须），如果简历没有覆盖，匹配分最高只能给 0.5；两条以上要压到 0.3 左右。

但这条规则**只存在于 prompt 的自然语言里**，代码侧一行实现都没有——模型返回 0.9 照样入库。唯一的执行力在离线评测脚本里，那是抽样的、事后的、不阻断的。

把它落成代码要解决一个问题：Python 怎么知道哪条要求是"强制性"的？直接信模型的标注很危险——**这条规则会把分数从 0.85 一把压到 0.3，模型只要把 "preferred"（加分项）也标成强制，大批职位就会被误杀，比不做还糟。**

做法是要求模型给出证据：标了强制性，就必须把 JD 原文里那一小段原话**逐字照抄**过来，不许翻译、不许转述。然后程序拿这段话回 JD 原文里找：

- 找得到 → 确认是强制要求，参与封顶
- 找不到（模型转述了、或者根本是编的）→ **当作不是强制要求**，退回没有这条规则时的行为

这个"核不过就放过"（fail-open）的选择是刻意的：这条规则的误杀代价大于漏杀代价，宁可少封几个，不可错封一片。

还有一个细节值得说：封顶之后，模型**原始**的那个分数被单独保留下来了。因为评测脚本原本是靠"分数有没有超过上限"来检测 prompt 是否还被遵守的——一旦代码强制封顶，这条断言就必然通过，等于悄悄失去了检测能力。改成检查原始分数，评测才继续有效。

## 四、可观测性：为什么它最先做

前面三节的改动都有一个共同问题：**怎么知道它们有没有用？**

在此之前这个项目答不上来最基本的几个问题——这个月 LLM 花了多少钱、哪个功能最容易失败、哪个模型慢。适配器文件里连日志都没有，API 返回的 token 用量字段从来没被读取过。

所以第一步是给所有 LLM 调用加一条流水：每次调用记一行，包括属于哪个功能、用了哪个模型、耗时多久、花了多少 token 和钱、成功还是失败、失败是哪一类。埋点打在三个底层调用函数上——它们是全项目所有 LLM 调用的唯一出口，一处埋点全覆盖。

两个设计上的取舍：

**刻意不记录 prompt 原文。** 一次匹配分析的 prompt 是简历全文加 JD 全文，十几 KB；每天几十次调用，一年就是几百 MB，而这份数据 99% 的时间没人看。只记长度，足够回答"是不是 prompt 变长导致变贵或被截断"。所以这是"记了成本和用量、刻意没记原文"，不是完整审计——这一点在文档里如实写明了，没有说成"已实现完整审计"。

**观测代码绝不能成为新的故障源。** 埋点整段包了异常兜底，写库失败只打日志、原异常照常往上抛。这条有一个专门的回归测试盯着：注入一个必然抛错的写库回调，主流程仍然要正常返回结果。加一层监控结果把主功能搞挂了，是比没有监控更糟的事。

另外补了一个容易漏的失败模式：API 返回 200、但返回的文本根本不是 JSON。这在埋点看来是成功的，可它恰恰是最该统计的一类失败。现在解析失败会把那条流水回填成失败，并且把模型实际吐出来的前 500 字带在错误信息里——在此之前只能看到一句 `Expecting value: line 1 column 1`，完全看不出模型说了什么。

## 五、边界：现在没做什么

诚实地列一下，这些都是判断的结果，不是遗漏：

| 没做 | 什么条件下会做 |
|---|---|
| RAG / 向量检索 | 面试题库涨到几百上千条、必须截断到答案失真时，给这一个功能单独接 |
| 验证器模型二次核查 | 出现"确定性代码抓不到、但确实在编"的幻觉类型时才重新评估 |
| 置信度评分 | 有独立验证器之后才有意义；模型自报的不用 |
| 结构化输出 | 已识别为下一步最该做的一项，需要按任务逐个试点 |
| 对 `company_overview` 做事实核查 | 这是全项目唯一一个**输入里没有任何依据**的字段（模型凭自身知识写公司简介），没有原文可核对。目前只有 prompt 约束 + 离线评测里一个关键词检测 |
| 记录 prompt 原文 | 成本明显不划算，除非出现必须回溯具体 prompt 才能排查的问题 |

还有一件必须说清楚的：**上面所有手段合起来也不是"消除幻觉"，是把它从高压到低。** 匹配分数目前的定位仍然是"粗排"而不是"决策线"——用来决定先看哪些职位，不用来决定投不投。任何声称能彻底解决幻觉的说法都值得怀疑，包括对这个项目的说法。

## 六、如果要用一句话概括

这个项目在 AI 可靠性上的核心判断是：**与其让模型自我审查，不如让它给出可以被程序验证的证据。**

"照抄这一段的原文"、"把 JD 里那句 required 的原话贴过来"——这些要求本身不难，但它们把一个无法验证的断言（"我改的是第 5 段"）变成了一个可以用十几行 Python 确定性验证的断言。这比再叫一个模型来复核便宜得多、快得多，也可靠得多。
