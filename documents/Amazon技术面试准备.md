## 一、AWS 技术栈问题

**预计问法**："你了解 Amazon Bedrock 或者 Nova 吗？有没有用过 Amazon 自己的 AI 工具？"

### 回答稿

- 目前的技术落地经验基于 Anthropic Claude API 和 Dify 这类编排工具，原理上跟 Bedrock 是一致的
- Bedrock 本质上是把 Claude、Amazon 自己的 Nova 等多个基础模型放在一个统一托管平台上，省去的是模型这一层的运维负担
- PM 要做的判断还是同一件事：不同场景该用哪个模型、成本和效果怎么权衡——这正是在"AI 报告解读平台"项目里做的判断：先用效果最好的模型验证质量，再评估更便宜的模型做成本优化
- 如果加入以后要在 Bedrock 环境里落地，这套判断逻辑可以直接迁移过去，需要补的是 Bedrock、SageMaker 这些具体产品操作层面的熟悉度，预计能很快上手

### 解释

这版回答的策略是"不装懂，但也不露怯"：诚实承认没有 Bedrock 实操经验，但立刻证明判断逻辑（模型选型、成本权衡）是可迁移的，不让对话停在"没用过"这个尴尬点上。如果面试官继续追问 Nova 具体是什么，可以用这个类比接下去：**Bedrock = 一个"AI 模型租赁店"，店里有 Claude、Nova 等好几个牌子的引擎可以按需租用；Nova 是 Amazon 自己造的引擎品牌，通常比 Claude 便宜、能力略弱，是店里的一个选项；SageMaker 则是如果想自己从零训练/维护一个专属模型时用的工具箱**。只需要记住一句话：Bedrock 系 = 租模型，SageMaker = 自己造模型。不需要再往下背更多产品细节。

## 二、部署问题 — Signal 项目

**预计问法**："你的这个个人项目是怎么部署的？如果要正式上线你会怎么做？"

### 回答稿

- Signal 目前跑在本机，因为服务对象就是我自己，一个人用，没必要做复杂的分布式部署——这本身也是一个技术判断，不是没考虑过
- 如果要正式化、给更多人用，会做几件事：
  - 用 Docker 把应用容器化，部署环境保持一致，不依赖本机配置
  - 放到一个小型云实例上，比如 AWS Lightsail 或 EC2 最小规格，用户量不大不需要过度配置
  - 数据库继续用 SQLite 的 WAL 模式，单人或小规模使用完全够用，用户量上来了再评估切换 Postgres
  - 加一条定时备份，把数据库定期同步到云存储，防止实例出问题丢数据
- 核心思路：让部署复杂度跟实际使用规模匹配，而不是一上来就上大架构

### 解释

这类问题面试官很可能是想看你会不会走两个极端——要么完全没有部署概念，要么不管三七二十一堆一堆技术名词上去。这版回答刻意突出"复杂度要匹配使用规模"这个产品判断维度，而不是单纯罗列技术栈，这个角度通常比"我会用 K8s + 微服务"这种过度工程化的回答加分更多，也更符合你一贯的产品判断风格。

## 三、部署问题 — AI 报告解读平台

**预计问法**："这个企业级 AI 项目还没上线，你打算怎么部署/上线？"

### 回答稿

- 部署实现是工程团队在做，但作为 PM 定义了从 0 到上线的完整节奏，分六个阶段：
  - **第一阶段，vibe-coding 搭 demo**：PM 根据需求，用 Claude Code 快速搭一个产品 demo，把整个链路先跑通；所需数据用脱敏后的真实数据，而不是完全人造数据，因为真实数据的分布和边界情况是合成数据很难覆盖的
  - **第二阶段，部署到 QA 环境**：工程师把这个功能部署到 QA 环境，开放给公司内部业务线人员访问、试用 demo，收集第一轮反馈
  - **第三阶段，迭代完善**：基于内部反馈，迭代功能和流程本身，不只是修 bug，也包括流程设计是否合理
  - **第四阶段，多客户联合 demo review，决策点**：拿完善后的版本跟多个客户一起 review，这里有一个明确的决策点——是否继续往下投入；这一步是为了确认"技术上没报错"和"业务上是对的、客户认可"是两件不同的事，只有两者都成立才值得继续
  - **第五阶段，MVP 上线（beta）**：开放给客户实际试用，同时设置每日 token 使用上限，控制成本和风险；这个额度机制全量上线后也会保留，从"控制风险"过渡成"分层定价"
  - **第六阶段，基于真实使用迭代**：上线不是终点，根据用户实际使用情况和反馈持续完善
- 额外的技术判断：agent 相关功能应该跟核心产品做独立部署，走更灵活的发布路径
  - 核心产品发布周期比较保守，改动影响所有客户稳定性；AI/agent 这层迭代速度快得多——模型在更新、prompt 在优化、还在做成本效果权衡实验
  - 如果绑定在核心产品发布节奏里：一是拖慢 AI 功能迭代速度，二是把 AI 部分还不够成熟的风险传导给核心产品稳定性
  - 独立部署能做到：AI 功能更高频发布和回滚，不用等核心产品发布窗口；出问题时爆炸半径隔离在 AI 服务本身，不影响核心功能；资源和成本可以独立扩缩容，因为 LLM 调用延迟和成本特征跟传统后端服务完全不同

### 解释

这版回答比之前更强的地方在于，第一阶段直接点名"用 Claude Code 做 vibe-coding"——这正好对应 JD 原文里"develop AI applications for simple use cases through vibe-coding and Amazon AI tools"这句话，等于用一个真实流程细节直接回答了 JD 的硬需求，而不是抽象地说"我会 vibe-coding"。

第四阶段的"决策点：是否继续"也是一个加分设计——它说明你不是走完流程就无脑上线，而是在关键节点做真正的取舍判断，这跟你故事 6（BlueStacks Mod/直播两次主动止损）体现的判断逻辑是一致的，面试官如果追问"如果 review 结果不好怎么办"，可以直接接故事 6 的止损逻辑。

第一、二阶段"PM 搭 demo → 工程师部署 QA"这个分工也值得注意：既展示你自己动手的能力（呼应故事 4 追问预案的 Sell before Build 模式和第九节的"年代感"话术），又清楚划了工程团队的边界，不会让人觉得你在抢工程师的活。

⚑ 如果面试官追问"脱敏之后数据还能代表真实场景吗"，可以提前想好一句兜底：脱敏只处理具体数值和身份信息，不改变数据的分布结构和统计特征，所以对模型行为的测试仍然是有效的——这是一个大概率会被追问的点，建议提前准备好。

## 四、模型上线前怎么判断 ready（LLM 和传统 ML 分开答）

**预计问法**："你怎么评估一个 AI agent / LLM 功能上线前是否 ready？"（大概率会追问"传统预测模型呢，是不是也这么判断"——所以提前把两条线分开准备）

### 回答稿 — LLM / 生成式 AI 功能

- **离线评估**：用一个标注过参考答案的 golden test set 把输出跑一遍，对每条输出打分——是否基于给定数据/context（groundedness）、事实是否准确（factuality）、有没有自相矛盾、格式是否合规
- **评分方式结合多种手段，不是纯人工**：
  - 用 LLM-as-a-judge 做大范围的质量和事实性打分——这正是 Amazon Bedrock Model Evaluation 原生支持的能力，用一个模型给另一个模型的输出打分，既能打 correctness、completeness 这些质量指标，也能打 harmfulness、拒答率这些 responsible AI 指标
  - RAG 场景额外用 groundedness scorer 验证输出是否真的基于检索到的内容
  - 高风险场景保留人工抽样复核
- **流程上要做到"eval-gated"**：prompt 或模型版本一变，必须先跑过这套自动化评估才能往下走，不能靠人工肉眼判断——这跟 Signal 项目里 8 个自动化测试套件（LLM 调用 mock 掉）保证的是同一个原则：不依赖模型当次返回的不确定性
- **防御要分层叠加**：system prompt 约束 + RAG grounding + 实时监控，这三层叠加能把幻觉率大幅降低（行业数据是 71%-89%），呼应第七节讲的分层防御设计
- **上线后**：持续监控评分均值有没有滑坡、做 PII 过滤、按场景控成本、出问题时要有可回放（replay）的排查机制

### 回答稿 — 传统 ML / 预测类模型

- **离线评估**：按任务类型选指标——分类问题看 precision/recall/AUC，预测类看 MAPE/RMSE 这些误差指标
- **backtest 有局限，不能只靠它**：在历史时间窗口上回测，但回测看不到被模型拒绝的样本、看不到生产环境的数据问题、看不到运营侧实际使用情况，所以不能靠回测结果就直接全量切换
- **shadow 测试**：新模型（challenger）先在生产环境"影子模式"跑，接收和现有模型（champion）同样的输入做对比，但不影响任何实际决策——零风险验证新模型的行为，但这一步看不出 challenger 的决策效果好不好
- **确认没问题后做小流量灰度上线**，统计显著性验证效果，再逐步扩大范围
- **上线后用 champion-challenger 机制持续跑**，配合自动化 drift 监控和回滚——这正是我在 DemandTec 做模型监控平台的思路：主动追踪每次预测的准确率，支持多维度下钻定位问题，在客户发现异常之前自己先发现

### 一句话收尾

- 这两条线流程细节不一样，但底层逻辑是一致的：上线前用离线指标和小范围验证控制风险，上线后靠持续监控替代"一次性判断"——ready 从来不是终点，是一个要持续维持的状态

### 解释

面试官如果懂技术，大概率会追问"LLM 和传统预测模型的评估是不是一回事"，这版回答提前把两条线拆开准备，避免被问到细节时露怯。两条线各自都能落到你的真实项目上——LLM 部分对应 Signal 的自动化测试和第七节的分层防御，ML 部分对应 DemandTec 的模型监控平台，面试官追问任何一层都有真实案例可以展开。

特别值得注意的是"LLM-as-a-judge"这个点——它是 Amazon Bedrock Model Evaluation 自己的原生功能（2025 年 3 月 GA），主动提到这个，等于是在用面试官自己公司的产品语言回答技术问题，比泛泛讲"我们会做人工评审"更有针对性。shadow 测试 / champion-challenger 这两个词是 MLOps 里的标准术语，如果面试官是数据科学或工程背景，讲出这两个词本身就是一个"你懂行"的信号。

### 追问预案：这套 LLM 评估方法怎么落到你实际做的项目里？

**预计问法**："这些评估方法听起来很完整，具体你在自己的项目里是怎么用的？"（这是一个大概率的追问——面试官想看你是真懂还是背了个框架）

### 回答稿

- 拿"AI 报告解读平台"这个项目具体说：
  - **golden test set 怎么建**：针对定价场景解读、what-if 分析解读、offer 历史分析这几个场景，各收集一批脱敏后的真实历史报告，配上人工写好的"标准解读"作为参考答案，形成评估集
  - **LLM-as-a-judge 用在哪**：最直接的应用场景是"评估更便宜模型能不能替代 Claude"这一步——每次要测试一个更低成本的模型时，让 judge 模型把新模型的解读和 Claude 的解读、以及人工参考答案做对比打分，不用每次都靠人工主观感觉"这个效果差不多"，这样才能把故事 1 里"效果没差别就换便宜模型"这个判断标准做到可量化、可复现
  - **groundedness check 怎么落地**：这其实就是我们已经在做的"要求输出引用具体数据点作为依据"这件事的技术实现——自动检测输出里提到的数字/结论是否真的出现在原始输入数据里，一旦发现输出引用了输入没有的内容，直接标记为潜在幻觉，触发人工复核而不是直接展示给客户
  - **eval-gated 怎么接入现有流程**：项目现在是 Demo 到 MVP 阶段，可以在这个阶段就把"每次 prompt 修改或模型切换，必须先跑一遍这套 golden test set + 打分"设成硬性门槛，跑不过分数线不能推给灯塔客户，而不是靠"感觉改好了"就上线

### 解释

这版追问预案的作用是防止"背框架"这个印象——上一版回答讲的是通用方法论，面试官如果追问"具体怎么用"，你需要立刻能把每个抽象概念（golden test set、LLM-as-a-judge、groundedness）精确对应到项目里的具体动作，而不是重复一遍定义。这里的关键技巧是：每一个技术方法都对应到故事 1 里已经讲过的一句话（"引用具体数据点作为依据"→ groundedness check；"效果没差别就换便宜模型"→ LLM-as-a-judge 做量化对比），显得整个技术框架不是这次面试现学的，而是你一直在用、只是刚好有对应的行业术语。

## 五、Agent 工具编排 / human-in-the-loop 设计思路

**预计问法**："描述一下你设计 agent 工具编排 / human-in-the-loop 的思路。"

### 回答稿

- 核心原则：高风险动作必须有人工确认点。举两个例子：
  - **DemandTec 定价决策 agent**：先定义清楚哪些是"只读/分析类"动作（拉取数据、生成场景分析），agent 可以自主执行；哪些是"写入/变更类"动作（调整定价、提交定价系统），必须经过人工确认。工具编排上用 Dify 管理，每个工具定义成明确的 action，写入类 action 执行前插入人工审核节点
  - **Signal 项目**：用 Playwright 实现浏览器自动化，把安全边界写进架构本身而不是 prompt 里——自动化只能填表单，永远不能点提交，提交动作必须自己手动完成
- 设计逻辑：human-in-the-loop 不应该靠 prompt 约束模型"不要做危险的事"，因为模型行为不是 100% 确定的；真正可靠的做法是在架构层面把危险动作物理隔离出来，让模型根本没有能力越权执行

### 解释

这版回答的核心亮点是"架构层安全边界 vs prompt 层约束"这个区分——很多候选人只会说"我在 prompt 里加了限制"，你能讲出"prompt 约束不可靠，要做到架构级隔离"，这个判断力本身就是加分项，而且是用两个真实项目（DemandTec agent + Signal）互相印证的，可信度高。

## 六、业务需求转技术需求的案例

**预计问法**："讲一个你需要把业务需求转成技术需求、并和工程对齐的例子。"

### 回答稿

- 案例：Auto-DG 自动化需求组分派项目
  - 背景：销量预测是两阶段架构，先在需求组层面做总量预测，再拆分到单品，架构成立的前提是需求组要分得合理；但分组过去完全靠人工完成
  - 业务侧提的需求是"预测不准，能不能提升准确率"——这是业务语言问题，不是技术需求
- 第一步，把业务问题拆解、定位根因：不是预测模型不行，而是上游分组质量不一致、不可复现，规模也覆盖不了大型零售商的 SKU 量级
- 第二步，把业务需求转成明确的技术需求：把人工分组流程自动化，保证分组结果的可复现性和可扩展性
- 跟工程团队对齐时，给的不是模糊描述，而是明确评估标准——分组后组内单品销售特征离散度要低于某个阈值，分组质量要能用预测准确率的提升来验证
- 结果：不同业务维度下模型预测准确率普遍提升 5% 以上，交付能力不再受人工产能限制，可以支撑更大规模客户

### 解释

这个回答完整走了"业务问题 → 根因定位 → 技术需求转化 → 可验证的成功标准"这条链路，而不是直接跳到"我们做了什么"，这正是 Dive Deep 和 Are Right, A Lot 想考察的思维过程。用 Auto-DG 而不是重复用故事 1/2，是为了在技术轮里展示一个此前材料没重点讲过的案例，避免面试官觉得你只有那两三个故事可讲。

## 七、Responsible AI / 数据隐私

**预计问法**："你怎么看待 AI 产品里的 responsible AI / 数据隐私？"

### 回答稿

- responsible AI 不是单点技术方案，而是要分层设计防御。以 AI 报告解读平台为例：
  - **事前（prompt 层）**：要求模型必须基于给定数据回答，不能引申推断超出数据范围的结论
  - **事中（生成层）**：生成结果标注置信度、引用具体数据点作为依据，方便溯源校验
  - **事后（反馈层）**：human-in-the-loop 反馈机制，高风险场景（比如涉及定价决策的输出）设置更严格的人工复核门槛——风险分级思路，不是所有输出都一视同仁地信任
- 数据隐私：面向企业客户的商业敏感数据（定价策略、库存信息），访问权限和账号体系由 Platform 团队统一管理，自己也直接参与过账号登录和权限体系模块（MFA）的产品定义
- 核心原则：AI 的可信度不能靠承诺"模型不会出错"来建立，而是要让系统在出错时能被发现、被纠正，责任边界要提前设计清楚，不是出问题再补救

### 解释

把权限体系（故事 7 里的 MFA）和 responsible AI 串联起来，展示的是"这个设计原则在你不同项目里反复出现"，而不是临时想出来应付这道题的。这种跨项目的一致性是技术轮里比单个亮点故事更有说服力的信号。

## 八、NBS 场景 MVP 技术 case 完整演练

**预计问法**："如果要给这个 AI Agent 产品定义一个 MVP，你会优先做什么？为什么？"（用一个具体场景走一遍完整推演）

### 回答稿

- 场景：为新卖家做一个"合规材料智能预审 agent"
- **第一步，用户和场景**：目标用户是刚完成注册、准备入驻材料的新卖家，尤其是对目的国合规要求不熟悉的跨境卖家；核心场景是提交营业执照、税务信息、品类资质材料时，卖家不知道材料是否齐全、格式是否合规
- **第二步，痛点和假设**：痛点是材料被人工审核打回的周期长，等待时间越长流失率越高；假设是提交前给出预审反馈能显著缩短卖家从注册到上架的周期
- **第三步，成功指标**：北极星指标是"首次提交通过率"，护栏指标包括合规漏检率（不能为了效率牺牲准确性）和卖家满意度
- **第四步，MVP 范围取舍**：不做全品类覆盖，先选结构标准化、规则明确的品类切入（比如营业执照），用传统分类/规则模型做初筛（需要高可解释性和高准确率）；生成式 AI 负责把模型判断"翻译"成卖家能看懂的修改建议，而不是直接做判断——ML 负责判断、GenAI 负责表达和交互
- **第五步，风险**：最大风险是误判导致本该通过的材料被拦下，增加卖家挫败感；MVP 阶段系统定位是"辅助建议"而不是"自动拒绝"，卖家仍可提交人工审核——风险分级和人工兜底
- **第六步，上线策略**：先在一个语言/地区试点，收集卖家实际反馈和误判案例，再决定要不要扩展到更多材料类型和地区

### 解释

这个回答完整走了第八节的六步框架（用户场景 → 痛点假设 → 成功指标 → MVP 范围 → 风险 → 上线策略），并复用了第五节 ML/GenAI 分工判断框架，没有为了这道题重新造一套逻辑，前后呼应、体系一致，是这份材料里"框架能落地成具体案例"的证明。如果时间够，可以准备第二个场景（比如"新卖家流失预警系统"）作为备用，走法完全一样，只是把第四步的判断换成"这是结构化数据分类问题，优先传统 ML"。

## 九、"技术背景年代感"弱项预案

**预计问法**：面试官深挖底层技术实现细节，或直接问"你自己写代码吗，写到什么程度？"

### 回答稿

- 工程背景是十几年前在 Capgemini 做 Java 后端开发起步的
- 这几年技术深度更多来自自己动手做的项目：
  - Signal 求职工具，1 万多行代码，自己设计了多 LLM 供应商抽象层、异步任务处理管道、浏览器自动化
  - DemandTec：自己搭了模型监控评估平台的原型
- 如果问"能不能看懂、能不能自己动手做原型验证一个想法"，答案是可以，而且是现在日常工作的一部分
- 如果问的是某个算法内部非常底层的实现细节，会诚实说明这个颗粒度是工程团队/数据科学家负责，自己的定位是判断和验证——对应公司在推的"Sell before Build"模式：自己搭原型验证方向对不对、需要看哪些指标，方向验证清楚后生产级实现交给工程团队
- 核心观点：技术背景的 PM 真正价值不在于比工程师更懂底层实现，而在于能准确判断需求的技术可行性和权衡在哪里，不会提出不切实际的方案——这个判断力从做工程师那几年就开始积累，没有断过

### 解释

主动划定"我能讲清楚到什么颗粒度"的边界，复用文档里已有的"Sell before Build"话术模板（故事 4 追问预案里已经验证过这个说法），把可能的短板转化成"技术判断力"这个长期优势的叙事。核心是不要等面试官问到答不上来才被动承认，而是主动、自信地划清边界。

## 十、数据 / SQL 类轻量问题

**预计问法**："如果你有一张卖家行为表，你会看哪些字段来判断流失风险？"（或类似的开放式数据分析场景题）

### 回答稿

- 会从几个维度看这张表：
  - **活跃度字段**：最近一次登录/操作时间、登录频次的趋势变化——最直接的流失信号
  - **业务健康度字段**：订单量或 GMV 的环比变化、库存周转、账户是否有未处理的合规警告——账户健康问题往往是流失前兆
  - **互动类字段**：有没有使用平台运营工具、有没有联系过客服——长期没有互动本身就是风险信号
- 拿到字段后不会只做简单规则判断（比如"7 天不登录就标记流失风险"），因为不同品类、不同规模卖家的基线活跃度不一样
- 会倾向于用一个轻量分类模型，把这些字段作为特征，输出流失概率分层而不是二元判断，业务侧可以按风险等级分配不同强度的干预资源（高风险用客户经理主动联系，中风险用自动化召回邮件）
- 这个思路跟传统机器学习负责判断类场景一致——流失预警本质是结构化数据的分类问题，可解释性和可复现性比生成式的灵活表达更重要

### 解释

用产品语言而不是纯 SQL 语法回答数据问题，同时呼应第五节的 ML 判断框架，保持整份材料风格前后一致。如果面试官进一步追问 SQL 细节，可以补一句"如果落到具体查询，我会按卖家 ID 分组、结合窗口函数看时间趋势变化"，但不需要主动展开，除非对方明确要看 SQL 语法本身。

## 十一、NBS AI 现状与差异化方向（2026-08 最新调研）

**预计问法**："你对我们现有的 AI 产品/Seller Assistant 了解多少？"

### 回答稿

- Seller Assistant 2025 年 9 月升级成 agentic AI，基于 Bedrock、Nova 和 Claude
- 现有能力：监控账户健康、生成健康状况总结、分析需求模式给出补货建议、主动提醒缺失合规文件、广告优化
- 目前对美国卖家免费开放，欧盟和英国扩展计划 2026 Q1，完全自主执行能力预计 2026 Q2 上线
- 今年 3 月上线的 Sellers Canvas：建立在 Seller Assistant 的 agentic 架构之上、同样由 Bedrock 驱动的交互式可视化工作台，卖家可以用自然语言探索经营数据、做场景模拟，系统直接生成可视化结果和行动建议——采纳率接近 90%
- Sellers Canvas 这个产品思路和"AI 报告解读平台"高度一致，都是把客户看数据的成本从"需要专业分析"降到"自然语言就能问"，这是判断这类产品价值的核心逻辑

### 解释

这个回答证明你做了扎实的功课（具体时间点、具体数字都对得上），并立刻把公司现有产品和你自己的真实项目做类比，把"了解贵司"这种客套话变成了有实质内容的连接。90% 采纳率这个数字是很好的记忆锚点，建议背下来。

---

**预计问法**："基于你对我们现有产品的了解，你觉得 NBS 这个团队还有哪些可以拓展的 AI 方向？"

### 回答稿

- Seller Assistant 和 Sellers Canvas 覆盖的更多是已入驻卖家的日常运营
- NBS 的定位是新商机与新卖家，真正有差异化空间的是卖家生命周期更早、更聚焦"新"这个阶段的场景，而不是重复造一个通用账户管理工具
- 三个方向：
  - **入驻前的选品和市场准入判断**：潜在卖家还没注册前，基于类目竞争度、预计流量、合规门槛，给出"这个市场值不值得进入"的量化建议——比现有工具更早一环，直接影响注册转化率
  - **专门针对新手期校准的流失预警模型**：新卖家"前三个月没订单"到底是正常观察期还是流失信号，跟成熟卖家基线完全不一样，不应该复用通用模型
  - **按生命周期节点主动触发的引导 agent**：现有工具更多是卖家来问、系统响应，可以把交互模式往前推一步，按卖家所处节点主动推送下一步该做什么
- 补一句留有余地的话：这些只是基于公开信息和自己的产品判断做的推测，实际团队的优先级和技术约束，很期待能在这轮聊到更多细节

### 解释

最后一句"这些只是基于公开信息的推测"很重要——展示自信判断的同时保持谦逊，避免显得"我比你们更懂你们的业务"，这个分寸感在面试里很关键，尤其是对 Think Big 和 Are Right, A Lot 这两个 LP 的平衡。

### 可用的反问问题

- "我看到 Seller Assistant 和 Sellers Canvas 已经覆盖了已入驻卖家的日常运营，NBS 团队是往新卖家生命周期更早的阶段延伸，还是在做更细分的模型校准？"
- "今年 3 月 Amazon 更新了 Business Solutions Agreement，加入了 Agent Policy，要求平台上的自动化系统自证身份、AI 生成的 listing 要有人工审核——这个新规对 NBS 内部正在做的 agent 类项目，在设计和上线节奏上有没有直接影响？"

### 补充：2026 年 3 月 Agent Policy 新规（合规弱项搭桥用）

可以接在第十节"薄弱点应对"里"全球贸易合规是弱项"这一条之后使用：

- 最近在关注 Amazon 今年 3 月更新的 Business Solutions Agreement 里新增的 Agent Policy，要求平台上运行的自动化系统要能自证身份、遵守规则，AI 生成的 listing 必须有人工审核
- 这跟"AI 报告解读平台"里坚持做 human-in-the-loop 反馈闭环、以及分层防御设计的逻辑是一致的
- 核心原则：不管是 Amazon 对第三方开发者的 agent 要求，还是自己做企业 AI 产品时的责任设计，自动化系统的自主权要有边界，高风险动作要能被追溯和人工介入

这段直接把"你了解最新平台政策"和"你自己的产品设计原则"绑定在一起，用来回应"全球贸易合规是弱项"这个薄弱点，比单纯说"我会学习"更有说服力。
