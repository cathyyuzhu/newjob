# ML 学习实践总结：用 jobs.db 真实数据预测"收藏 vs 忽略"

> 记录时间：2026-08-21
> 定位：这是一次机器学习基础学习练习，用 `newjob` 项目里真实积累的求职数据当教材，**不是产品功能**，代码独立存放在 `learn_ml/` 目录，不接入 app、不进 `spec/roadmap.md`。

## 为什么做这件事

在讨论"这个项目里有没有需要 ML 的地方"时，发现一个可以用真实数据练手的场景：`jobs.db` 里已经积累了上百条职位、每条都有用户真实做过的"收藏"或"忽略"决定——这是天然的监督学习标签。借这个真实、有意义但体量不大的数据集，从零走一遍标准的机器学习分类工作流，目标是学概念、建直觉，不是做出一个要上线的功能。

## 最初想解决的问题

能不能训练一个模型，从职位的各种信息（LLM 打的匹配度、公司国籍、来源网站、搜索关键词……）里学会预测用户会"收藏"还是"忽略"这条职位，产出一个比现成的 `overall_match`（LLM 语义匹配度）更贴合用户个人偏好的"个人化匹配度分数"。

## 用到的数据

- 数据源：`jobs.db` 的 `jobs` 表 + `job_dismiss_reasons` 表（忽略原因）
- 初始有标签数据：110 条（`status='reviewed'` 收藏 17 条 / `status='dismissed'` 忽略 93 条），类别比例约 15% / 85%，明显不均衡
- 两轮数据清洗（详见下文）后最终用于训练：**97 条**（收藏 16 / 忽略 81）
- 候选特征：`overall_match`（LLM 匹配度）、`company_origin`（外企/国内）、`site`（Indeed/LinkedIn）、`keyword`（搜索关键词，4种取值）

## 走过的标准工作流，以及每一步的真实结果

### 1. 数据探索（EDA）
- 发现类别不均衡（85%/15%）——记下这个数字，后面会用来戳穿"准确率会撒谎"
- `overall_match` 两组分布有差异（收藏组均值0.71 vs 忽略组0.53）但有重叠，不能简单卡阈值分开
- 发现一个可疑信号：`company_origin='domestic'` 的职位当时 0 条被收藏——高度怀疑是"页面默认筛选外企"导致的选择偏差，而非真实的偏好判断（后续验证发现证据不足以下定论，见下文"标签质量排查"）

### 2. 基线模型（Baseline）
- 用 `DummyClassifier(strategy="most_frequent")`（无脑预测"忽略"）
- **Accuracy 高达 83~84%，但"收藏"类的 precision/recall/f1 全是 0**——这是整个练习最核心的教训之一：**数据不均衡时，准确率不能反映模型有没有学到东西**，必须看 precision/recall/F1/AUC

### 3. 第一个真实模型：单特征逻辑回归
- 只用 `overall_match` 一个特征训练逻辑回归，用 `StratifiedKFold`（5折）交叉验证评估
- 默认权重版本：预测结果表面看跟基线一样（recall=0），但 **AUC=0.80**，说明模型确实学到了排序能力，只是默认 0.5 判定阈值在不均衡数据上过于保守
- `class_weight='balanced'` 版本：recall 冲到 0.8+，precision 明显下降——纯粹是判定阈值的取舍，AUC 几乎不变，证明不是"模型变聪明了"

### 4. 加入更多特征
- one-hot 编码 `company_origin`/`site`/`keyword` 后训练完整特征逻辑回归
- **反直觉的结果：完整特征集的 AUC（0.79）反而比单特征模型（0.82）更低**——97条样本、17条正例，撑不住 6 个参数，属于轻度过拟合的信号
- 专门做了"去掉 company_origin"的对照：AUC 从 0.79 掉到 0.75，说明这个特征确实在完整模型里贡献了预测力，但结合它跟选择偏差的关联，这份贡献不能照单全收

### 5. 过拟合专项演示（决策树深度对照）
- 决策树不限深度 vs 各级深度限制，对比"训练集分数"和"交叉验证分数"
- 训练集 accuracy/AUC 随深度单调上升，逼近 1.0（几乎背下所有样本）
- 交叉验证 AUC 在中等深度见顶后下降——标准过拟合曲线
- **意外但很有教学价值的发现**：交叉验证 accuracy 反而是深度越深越"高"，跟 AUC 走势相反——拆开看才发现，是深度越深的树在没见过的新数据上更倾向退回预测多数类（忽略），蒙对次数变多、accuracy被抬高，但对真正关心的"收藏"类识别能力（recall）反而更差。**再一次印证"不能只看 accuracy"，这次是在过拟合场景下的翻版**

### 6. 标签质量排查（用户提出的关键问题）
用户指出："标记忽略不一定是因为不匹配，还可能是职位重复/已下架等原因，这些不该被当成负样本。"

查 `job_dismiss_reasons` 表，找到 4 条这类"记录问题而非偏好判断"的忽略：
| job_id | 原因 |
|---|---|
| 58 | 跟linkedin重复 |
| 87 | 重复 |
| 77 | 重复（该条现在状态其实是"已收藏"，标签历史本身是脏的） |
| 88 | 公司停止招聘 |

把这 4 条从训练数据里整行剔除（`learn_ml/data.py` 的 `NON_PREFERENCE_REASON_KEYWORDS` 过滤逻辑），重新跑一遍全流程：单特征模型 AUC 从 0.799 提升到 **0.820**，结论方向不变但更可信。

**局限**：93 条忽略记录里只有 14 条填过忽略原因（这个功能可跳过），能排查出来的只是"冰山一角"——没填原因的忽略里可能还混着同类情况，没法排查干净。

### 7. 最终结论：能不能产出"更准的个人化匹配度分数"
用单特征模型的 `predict_proba` 概率跟 `overall_match` 并排对比，发现两者相关系数 **0.999**——这不是好消息，是一个数学上必然的结果：**单特征逻辑回归的输出，必然是这一个特征的单调函数**，不可能对职位重新排序。这是这次练习里我自己设计上的一个疏忽（写脚本前没想清楚这个数学性质），但也是很有价值的教训。

真正能产生不同排序的是完整特征模型，但它的分歧主要来自可信度存疑的 `company_origin`，且交叉验证表现更差。

**最诚实的最终答案**：拿现在这 97 条数据（16条正例），**做不出一个比 `overall_match` 更准的个人化匹配度分数**——不是流程哪里做错了，是老老实实走完整套标准流程之后，数据本身给出的答案：样本量不够支撑"比现成 LLM 判断更聪明"这件事。这本身是一个真实、常见、有价值的 ML 结论。

## 学到的核心概念清单

- 监督学习：用历史标签（人的真实决定）训练模型模仿判断
- 类别不均衡：accuracy 在这种数据上会撒谎，要看 precision/recall/F1/AUC/混淆矩阵
- 交叉验证（`StratifiedKFold`）：小样本下比单次 train/test split 更可靠
- 基线模型：任何模型都要有"不学习也能达到的水平"做参照
- 特征工程：one-hot 编码类别变量、哑变量陷阱（`drop_first=True`）
- 特征不是越多越好：小样本下参数太多会过拟合，交叉验证表现可能不升反降
- 过拟合：训练集分数 vs 交叉验证分数的差距是过拟合程度的信号；决策树深度是最直观的例子
- 判定阈值 vs 排序能力：AUC 衡量排序能力，不依赖 0.5 这个默认阈值；`class_weight='balanced'` 只是调整阈值取舍，不是让模型变聪明
- 标签泄漏（label leakage）：不能用"结果发生之后才有的信息"去预测结果本身（忽略原因不能当特征）
- 标签质量 / 数据收集过程偏差：原始标签字段不一定干净，要结合业务知识甄别（重复入库、职位下架 ≠ 真实偏好判断）
- 数学性质先于实验：单特征模型的输出必然是该特征的单调函数，这类结论应该在写代码前就想清楚，而不是跑出来才发现

## 产出文件

全部在 `learn_ml/` 目录，独立于生产代码：

- `data.py`：共享的数据加载与清洗逻辑（丢弃 `overall_match` 缺失行 + 剔除"记录问题"类忽略）
- `step1_explore.py`：数据探索
- `step2_baseline.py`：DummyClassifier 基线，演示 accuracy 陷阱
- `step3_first_model.py`：单特征逻辑回归，交叉验证评估
- `step4_more_features.py`：完整特征逻辑回归，含 company_origin 对照实验、系数解读
- `step5_overfitting_demo.py`：决策树深度对照，过拟合演示
- `step6_score_compare.py`：个人化分数 vs `overall_match` 对比

运行方式（Windows，注意编码）：

```bash
cd newjob
PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe learn_ml/step1_explore.py
# ...其余脚本同理
```

依赖 `scikit-learn`、`matplotlib`（已装进 `.venv`，未写入主 `requirements.txt`——这是学习练习的额外依赖，不是产品运行时依赖）。

## 以后想重新做这件事该怎么办

数据量是这次练习最大的硬约束（97条样本、16条正例）。往后随着继续用这个 app 求职、`jobs.db` 里的收藏/忽略记录持续增加，可以直接重跑这套脚本（`data.py` 到 `step6` 的流程完全不用改），正例攒到大几十条以上时，结论很可能会不一样——尤其是"完整特征集是否真的能超过单特征模型"这个问题，目前的结论受限于样本量，不是永久性结论。

如果以后真想把这类分数集成进 app 本身（不只是学习练习），需要先解决：
1. 样本量是否足够（建议正例至少到 50+ 再认真考虑）
2. `company_origin` 的选择偏差问题要么解释清楚要么想办法排除
3. 标签清洗规则（剔除"记录问题"类忽略）要不要用同样的关键词匹配做成正式的数据清洗步骤
